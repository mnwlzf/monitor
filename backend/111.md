单体 Java 项目，核心思路是**在同一个 Spring Boot 应用内做逻辑模块划分**。采集、清洗、展示各成模块，共享一个数据源，但模块间通过接口或事件解耦，避免直接依赖。

参考 New API 和 Sub2API 的分层方式（router → middleware → controller → service → model/relay），以及 Spring Modulith 的模块化单体理念，给你一份可直接落地的单体结构。


## 顶层结构

```
upstream-monitor/
├── pom.xml
└── src/main/java/com/yourorg/upstream/
    ├── UpstreamMonitorApplication.java
    ├── common/          # 公共契约与工具
    ├── adapter/         # 上游适配器
    ├── collector/       # 采集调度
    ├── normalizer/      # 数据处理
    ├── query/           # 查询/展示服务
    ├── api/             # 对外 HTTP 接口
    └── config/          # 全局配置
```

这是**按业务领域分包**，不是按 model/controller/service 技术分层。每个包内部自带自己的 controller、service、repository，对外只暴露必要的接口。


## 各包职责

### common/ —— 公共契约

只放与具体上游无关、全项目共用的东西：

```
common/
├── contract/
│   ├── UpstreamAdapter.java     # 适配器接口，定义 fetch() 方法
│   ├── NormalizedRecord.java    # 标准化记录模型
│   └── RecordType.java
├── exception/
│   ├── UpstreamException.java
│   └── AuthException.java       # 认证失败（New API token 过期等）
└── util/
    └── TimeUtils.java
```

`UpstreamAdapter` 接口：

```java
public interface UpstreamAdapter {
    String getType();                       // "newapi" | "sub2api"
    List<NormalizedRecord> fetch(FetchContext context);
}
```

### adapter/ —— 上游适配器

这是项目的核心复杂度所在，按上游类型分子包，每个子包自成体系：

```
adapter/
├── newapi/
│   ├── NewApiAdapter.java          # 实现 UpstreamAdapter
│   ├── NewApiClient.java           # HTTP 客户端，处理认证头
│   ├── NewApiMapper.java           # 响应 → NormalizedRecord
│   └── model/
│       ├── UserSelfResponse.java
│       └── LogEntry.java
├── sub2api/
│   ├── Sub2ApiAdapter.java
│   ├── Sub2ApiClient.java
│   └── Sub2ApiMapper.java
└── AdapterRegistry.java            # 按 type 查找适配器
```

New API 的适配器要点：普通用户只能调 `/api/user/self`、`/api/log/self`，认证需要 `Authorization` + `New-Api-User` 两个头。Sub2API 通过 `/v1/usage` 获取用量，Bearer Token 认证。

### collector/ —— 采集调度

```
collector/
├── CollectService.java         # 采集主流程
├── Scheduler.java              # 定时调度（Spring @Scheduled）
├── entity/
│   ├── RawRecordEntity.java    # 原始 JSON 落地
│   └── AccountEntity.java
└── repository/
    ├── RawRecordRepository.java
    └── AccountRepository.java
```

采集流程：`Scheduler` 定时触发 → `Adapter` 拉取 → 原始 JSON 存 `raw_records` 表 → 发 `CollectCompletedEvent`。原始数据保留的意义是可以**重放**，上游字段变了或解析有 bug 时不用重新采集。

### normalizer/ —— 数据处理

```
normalizer/
├── NormalizeService.java       # 监听采集事件，执行清洗
├── NormalizePipeline.java      # 字段映射、单位统一、去重
└── event/
    └── CollectCompletedEvent.java
```

用 Spring 的 `@EventListener` 监听采集完成事件，把原始 JSON 清洗成业务表数据。这样采集和清洗解耦，采集挂了不影响已有数据的清洗。

### query/ —— 查询服务

```
query/
├── QueryService.java           # 读模型组装
├── dto/
│   ├── AccountSummary.java
│   └── UsageList.java
└── repository/
    └── UsageLogRepository.java
```

只做读查询，从业务表/物化视图取数，组装成 DTO 返回。**DTO 与 Entity 严格分离**，数据库表结构不直接暴露给前端。

### api/ —— 对外接口

```
api/
├── AccountController.java      # /api/v1/accounts
├── UsageController.java        # /api/v1/usage
└── HealthController.java       # /api/v1/health
```

Controller 只做参数解析和响应包装，业务逻辑在 query/ 和 collector/ 里。所有接口带 `/v1` 前缀，方便后续演进。


## 模块间依赖规则

这是让单体项目“好维护”的关键：

```
api ──► query ──► common
api ──► collector ──► adapter ──► common
collector ──► normalizer (通过事件，不直接调用)
```

- `common` 不依赖任何其他包
- `adapter` 不依赖 `collector` 或 `api`
- `collector` 发事件，`normalizer` 监听，两者不互相 import
- `query` 和 `collector` 不直接依赖，各自独立读数据库

如果后续觉得边界容易破，可以引入 **Spring Modulith**，它提供模块化验证，模块越界会在测试时报错。


## 配置与数据库

`application.yml` 里管理上游账号配置，密钥走环境变量：

```yaml
upstream:
  accounts:
    - name: newapi-a
      type: newapi
      base-url: ${NEWAPI_BASE_URL}
      auth:
        access-token: ${NEWAPI_TOKEN}
        user-id: ${NEWAPI_USER_ID}
```

数据库用 Flyway 管理迁移，核心表：`raw_records`（原始 JSON）、`accounts`（上游账号）、`usage_logs`（清洗后日志）、`collect_runs`（采集执行记录）。


## 为什么这样分

New API 和 Sub2API 虽然都是 Go 项目，但它们的分层逻辑（路由 → 中间件 → 控制器 → 服务 → 模型）值得借鉴。你的项目用 Java 单体实现时，把“按上游类型适配”作为第一分类维度，而不是按技术层横切，这样**新增一个上游只动 adapter 下一个子包**，不影响采集、清洗、展示的任何代码。这是让项目长期好维护的核心。
