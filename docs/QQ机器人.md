# QQ 机器人（OneBot + Spring AI）

不打开站点，直接在 QQ 里问「近 24 小时哪个号池账号缓存率最低」「平台余额还剩多少」，机器人查真实数据后回答。

## 架构

```
QQ 客户端 ──► NapCat / Lagrange / go-cqhttp（OneBot v11 实现）
                      │  反向 HTTP 上报（带 Authorization: Bearer <webhook-token>）
                      ▼
              POST /api/v1/bot/onebot
                      │
                      ├─ / 开头的命令  ──► 直接查库（不需要大模型）
                      └─ 自然语言      ──► Spring AI ChatClient ──► function calling ──► 同一批只读查询
                      │
                      ▼
              POST {api-base-url}/send_group_msg | /send_private_msg
```

所有查询都是**只读**的，机器人不会触发采集、删除等写操作。

## 1. 先跑一个 OneBot 实现（NapCat）

OneBot 只是**协议**，本身不是服务 —— 需要有个程序真的登录你的 QQ 账号。
个人开发者推荐 [NapCat](https://github.com/NapNeko/NapCatQQ)（官方 Docker 镜像 `mlikiowa/napcat-docker`）：

```bash
# 1) 起 NapCat（已包含在主 compose.yaml 里）
docker compose up -d

# 2) 从日志里拿 WebUI 的登录 token
docker compose logs napcat

# 3) 本机执行 SSH 隧道（WebUI 只绑在服务器的 127.0.0.1）
ssh -L 6099:127.0.0.1:6099 root@<服务器IP>

# 4) 浏览器打开 WebUI，扫码登录 QQ（建议用**小号**：自建机器人有风控/封号风险）
#    http://127.0.0.1:6099/webui?token=<上一步日志里的 token>
```

> 登录态与配置直接挂在宿主机 `/app/napcat/` 下（`qq` / `config` / `plugins` 三个子目录），
> 重启容器不用重新扫码。**NapCat 侧不需要 `.env`**：端口与目录都写在 `compose.yaml` 的 napcat 服务里，部署目录不同就改那三行 volume。

登录成功后，在 WebUI 的「网络配置」里开两样：

| 类型 | 作用 | 配置 |
|---|---|---|
| **HTTP 服务端** | monitor 通过它把回复发出去 | 容器内监听 `0.0.0.0:3000`（NapCat 侧固定），compose 映射到宿主机 `127.0.0.1:5000` |
| **HTTP 客户端（反向 HTTP 上报）** | NapCat 把收到的消息推给 monitor | URL `http://monitor:8080/api/v1/bot/onebot`，Header `Authorization: Bearer <MONITOR_BOT_WEBHOOK_TOKEN>` |

### 两个容器怎么互访

`napcat` 与 `app` 在**同一个 compose 文件**里，天然处于同一个网络（项目名 `monitor` → 网络 `monitor_default`），
所以直接用**容器名 + 容器内端口**互访，不经过宿主机端口：

| 方向 | 地址 |
|---|---|
| app → napcat（发消息） | `http://napcat:3000`（`MONITOR_BOT_API_BASE_URL`） |
| napcat → app（反向 HTTP 上报） | `http://monitor:8080/api/v1/bot/onebot` |

> ⚠️ 不要用 `host.docker.internal` 走宿主机端口：NapCat 的端口只绑在 `127.0.0.1`，
> 容器从网卡 IP 访问回环端口是连不通的。
>
> 宿主机端口被占用（`Bind for 127.0.0.1:xxxx failed: port is already allocated`）时：
> `docker ps` / `ss -lntp | grep <端口>` 找出占用者；或直接换端口 ——
> 改 `compose.yaml` 里 napcat 的 `ports` 映射（宿主机侧），容器内始终是 3000。

其它可选实现：Lagrange.Core、LLOneBot。`go-cqhttp` 已停更，不建议再用。

> 不想自建 QQ 客户端，可以走 **QQ 官方机器人开放平台**（不用挂 QQ、不怕封号），
> 但要主体资质与审核，协议也不同（Webhook + AppID/Secret），需要另外加一层适配。

## 2. 配置本服务

在 `.env` 里填：

```dotenv
MONITOR_BOT_ENABLED=true
MONITOR_BOT_WEBHOOK_TOKEN=<与 OneBot 侧一致>
MONITOR_BOT_API_BASE_URL=http://napcat:3000
MONITOR_BOT_API_TOKEN=<OneBot 的 access token，没设置就留空>

# 白名单：逗号分隔的群号 / QQ，留空表示不限制（建议显式配置）
MONITOR_BOT_ALLOWED_GROUPS=123456789
MONITOR_BOT_ALLOWED_USERS=987654321

# 群里是否需要 @机器人 才响应
MONITOR_BOT_REQUIRE_MENTION=true
```

重启后日志会出现 `QQ 机器人已接入大模型，支持自然语言问答` 或 `未配置大模型，QQ 机器人只支持命令`。

## 3. 使用

在**指定群**里 `@机器人`，或（仅管理员）私聊机器人后发送。
**平台级命令只在「指定群」生效**，群临时会话按「发起群」判定 —— 详见第 4 节。

| 命令 | 作用 | 谁能用 |
|---|---|---|
| `/help` | 用法 | 所有人 |
| `/我的余额` | 我自己的余额、冻结、累计充值、账号状态 | 平台用户（指定群） |
| `/我的用量 [窗]` | 我自己的请求数、Token、消耗，窗取 `today` / `7d` / `30d` | 平台用户（指定群） |
| `/我的密钥` | 我自己的 API Key 列表（密钥打码） | 平台用户（指定群） |
| `/我的错误 [时间窗] [状态码/关键词]` | 我自己的最近错误；不需要请求 ID，默认近 24 小时 | 平台用户（指定群） |
| `/我的信息` | 查看当前绑定的邮箱 | 所有人 |
| `/绑定 <邮箱>` | 绑定邮箱（也可由 `<QQ号>@qq.com` 自动匹配，无需绑定） | 所有人 |
| `/解绑` | 解除绑定 | 所有人 |
| `/天气 <城市> [天数]` | 实时天气与未来预报 | 所有人 |
| `/openai` | OpenAI 官方服务状态（中文）：总体状态、异常组件、进行中事件与更新时间 | 管理员 + 平台用户（指定群） |
| `/画图 <提示词>` | 生成一张图片并发出来（**全局限频：一分钟最多 3 张**） | 所有人 |
| `/平台` | 上游平台概览（账号数、异常数、余额合计） | 管理员 |
| `/号池 [时间窗]` | 号池账号的请求数、缓存率、首 Token，时间窗 `90m/1h/6h/12h/24h/7d/30d/90d`，默认 `24h` | 管理员 |
| `/采集` | 号池直连库增量采集状态（游标位置、数据滞后） | 管理员 |
| `/账号 <关键字>` | 按名称模糊查账号余额与状态 | 管理员 |
| `/变更 [条数]` | 最近的账号 / 密钥变更记录 | 管理员 |
| `/消耗 [条数]` | 全平台账号消耗排行：余额、今日消耗、累计消耗、累计请求，默认 10 条 | 管理员 |
| `/异常` | 异常账号名单：被停用 / 采集失败 / 凭证失效，并给出原因 | 管理员 |
| `/诊断 [时间窗]` | 错误概览、错误率、429/529、401/403、5xx、主要错误类型与问题账号，并给出建议 | 管理员 |
| `/错误 [时间窗] [状态码/关键词]` | 最近错误；不需要请求 ID，可按 429、5xx、限流、配额、账号名、模型名筛选；`/错误 #编号` 查看详情 | 管理员 |
| `/错误账号 [时间窗] [条数]` | 按账号统计错误排行，定位问题号池账号 | 管理员 |
| `/错误用户 <邮箱或ID> [时间窗]` | 指定平台用户的最近错误 | 管理员 |
| `/错误指纹 [时间窗] [条数]` | 按错误阶段/类型/状态码/provider_error_code/归一化消息聚合，展示影响面和消息样本 | 管理员 |
| `/错误趋势 [时间窗]` | 当前窗口与上一等长时间窗对比，判断错误是否突增，并列出指纹增量 Top 5 | 管理员 |
| `/错误变更 [时间窗]` | 结合错误指纹与分组/Key/账号变更时间，回答“是不是刚改了什么” | 管理员 |
| `/恢复错误 [时间窗] [条数]` | 上游失败但最终恢复的请求，以及最大尝试次数 | 管理员 |
| `/错误实例 [时间窗]` | 多个 Sub2API 实例的错误率、429/529、健康分对比 | 管理员 |
| `/入口拒绝 [时间窗]` | 无效 Key、Key 禁用、IP 限制、用户/分组禁用等入口拒绝统计 | 管理员 |
| `/错误日志 [时间窗] [级别] [关键词]` | 不需要请求 ID，按时间、级别和关键词查系统日志 | 管理员 |
| `/错误审计 [时间窗] [条数]` | 查看错误查询审计、限流拦截、动作排行和最近查询 | 管理员 |
| `/任务` | 定时任务的启用状态与最近一次执行结果（排查「采集是不是挂了」） | 管理员 |
| `/订单 <账号> [起] [止]` | 指定平台用户的订单：余额、汇总与明细；日期可省，默认近 30 天 | 管理员 |
| `/用户余额 <账号>` | 指定平台用户的余额、冻结余额与累计充值 | 管理员 |
| `/用户消耗 [日期]` | **所有用户**在指定日期的余额消耗排行（默认今天，支持「昨天」「前天」） | 管理员 |
| `/渠道状态 [时间窗]` | 按**平台 / 分组**聚合的渠道健康：请求数、成功率、首 Token、缓存率。普通用户只看自己有权限的分组 | 管理员 + 平台用户 |

> **`/我的*` 只能查发送者自己**：机器人用发送者邮箱解析出的 Sub2API 用户 ID 去查询，
> 不接受任何用户标识参数，也不存在「查别人」的入口。用户数据来自平台管理员只读接口，
> 错误数据来自 Sub2API 只读库。

命令前缀可用 `MONITOR_BOT_COMMAND_PREFIX` 改。**这些命令不依赖大模型。**

### OpenAI 服务状态

- `/openai`、`/openai状态` 或直接问「OpenAI 现在正常吗」，都会读取
  <https://status.openai.com/api/v2/summary.json>。
- 回复里的「查询时间」是机器人本次读取状态页的北京时间；「状态页最后更新」来自官方 `page.updated_at`，
  表示官方页面最近一次变更时间，可能是几天前，不等于本次查询时间。
- 返回内容统一翻译为中文：`none/minor/major/critical/maintenance` 会显示为
  「全部系统正常 / 轻微服务异常 / 重大服务异常 / 严重服务异常 / 计划维护中」，
  当前已收录的组件名和组件状态也会翻译。
- 该功能只对**指定群内的管理员和平台用户**开放；非指定群、陌生人和非平台用户仍按未知命令处理。
- 「OpenAI 服务状态监控」定时任务每 10 分钟采集一次。连续异常期间只向
  「指定群（平台功能）」发送一次告警；恢复正常后再次异常才会重新发送。
- 状态页本身不可访问时，定时任务会标记为 `FAILED`，但不会误判为 OpenAI 服务异常。

### 错误排障（不需要请求 ID）

用户端通常看不到请求 ID，因此错误命令按时间窗、状态码、模型、账号和关键词查询；
机器人会在结果里给出自己的「错误编号 #数字」，需要看单条详情时回复该编号即可。
错误列表支持分页：`/错误 1h 5 p2` 表示每页 5 条、第 2 页。

```text
/诊断 1h
/错误 1h 429
/错误 1h 5xx
/错误 1h 全部
/错误账号 24h 10
/错误用户 user@example.com 7d
/错误指纹 1h 10
/错误趋势 1h
/错误变更 1h
/恢复错误 1h 10
/错误实例 1h
/入口拒绝 1h
/错误日志 1h error 529
/错误审计 24h 20
/我的错误 24h
/我的错误 #123
```

原因推断会跨表关联：

- `users`：用户状态、余额、分组限制
- `api_keys`：Key 状态、额度、过期时间
- `groups` / `user_subscriptions` / `user_allowed_groups`：分组状态、订阅有效性、访问权限
- `accounts`：账号状态、可调度、限流/过载/临时不可调度、过期时间
- `usage_logs`：同用户/账号/模型在错误前后是否仍有成功请求

例如会直接指出「API Key 已禁用」「用户无分组权限」「订阅已过期」「号池账号限流中」「上游 529 过载」等原因，并给出置信度和处理建议。

错误命令需要 `SUB2API_DB_URL` / `SUB2API_DB_USERNAME`，并给只读账号授予
`ops_error_logs`、`ops_system_logs`、`ops_ingress_reject_aggregates`、`usage_logs`、`users`、`api_keys`、`accounts`、`groups`、`user_subscriptions`、`user_allowed_groups`
的 SELECT 权限。错误查询只要求连接信息完整，不依赖 `SUB2API_DB_ENABLED`（该开关只控制号池增量采集）。

### 主动错误告警

错误告警默认关闭，配置入口在页面的 **系统设置 → QQ 机器人 → Sub2API 错误主动告警**，保存后立即生效，不需要改环境变量或重建容器。

页面上可以配置：

- 是否启用错误告警
- 对比窗口（默认 15 分钟）
- 最小触发数量（默认 5）
- 突增倍数（默认 1.5）
- 冷却时间（默认 30 分钟）
- 接收群 / 私聊 QQ，支持添加备注，群和私聊可以同时配置

定时任务默认每 5 分钟检查一次错误、429/529 和入口拒绝是否相对上一周期突增；同一告警在冷却期内不重复发送。未配置接收人或只读库时自动跳过。告警任务本身也可以在「定时任务」页面停用。

### 查询审计和限流

错误命令和自然语言错误工具查询共用同一套限流：按 QQ 用户默认每分钟最多 12 次。每次查询会写入 `bot_error_query_audits`，记录用户、动作、参数、是否放行和耗时。管理员可用 `/错误审计 24h 20` 查看审计和限流拦截情况；审计查询本身也会在回复后写入一条记录。

### 长回复会自动转成表格图片

渠道状态、账户余额、号池明细这类内容本质是**表格**，一长串项目符号既对不齐也不好扫读。
超过 `回复最大长度`（默认 900 字）的回复会渲染成 PNG 图片发送，形态分两种：

**普通数据表** —— 表头浅灰底、数值列右对齐、隔行浅色：

| | |
|---|---|
| `/平台` | 平台 / 类型 / 账号数 / 异常 / 余额合计 |
| `/账号 <关键字>` | 账号 / 平台 / 状态 / 余额 / 已用额度 / 最近采集 |
| `/变更` | 时间 / 平台 / 内容 |
| `/采集` | 游标位置 / 最后推进 / 最新明细 / 数据滞后 |
| `/消耗` | 账号 / 平台 / 余额 / 今日消耗 / 累计消耗 / 累计请求 |
| `/异常` | 账号 / 平台 / 原因 / 余额 / 最近采集 |
| `/诊断` | 时间窗 / 请求数 / 错误数 / 错误率 / 业务限制 / 429/529 / 401/403 / 5xx |
| `/错误` | 编号 / 时间 / 分类 / 状态 / 模型 / 用户或账号 / 消息 |
| `/入口拒绝` | 原因 / 路由 / 协议 / IP / 用户或 Key / 次数 / 最近 |
| `/错误日志` | 时间 / 级别 / 组件 / 消息 |
| `/任务` | 任务 / 处理器 / 状态 / 最近执行 / 结果 |
| `/订单` | 创建时间 / 类型 / 支付方式 / 到账 / 实付 / 状态 / 支付时间 |
| `/用户消耗` | 用户 / 请求数 / Token / 标准费用 / 实际消耗 |
| `/渠道状态` | 平台 / 分组 / 状态 / 请求 / 成功率 / 首 TOKEN / 缓存率 |

**号池热力图** —— 和前端「号池 → 趋势矩阵」页同一张表：左侧是账号汇总
（缓存率 / 首 Token / 每秒 Token / 请求），右侧是等宽时间桶的色块矩阵，
颜色规则与页面完全一致（`hsl(比率 × 120, 62%, 52%)`，越绿越好、越红越差，
灰色表示该时段没有流量）。无流量的渠道单独用一段文字列出，不占表格行。

图片宽度按内容自适应：列多时会自动变宽（上限 2400px），只有超过上限才压缩列宽。
`MONITOR_BOT_IMAGE_WIDTH` 是最小宽度（默认 760px）。

### 自然语言问答怎么拿到同一张热力图

大模型只能写 Markdown，画不了图，所以它需要拿到**细粒度**的数据。为此：

- 管理员人设被要求：涉及号池趋势 / 热力图 / 时间分布时**必须调用 `poolHeatmap` 工具**，
  并把它返回的 `[[HEATMAP:24h]]` **标记原样**放进回答
- **热力图不由大模型输出，而是由后端按标记确定性渲染**。原因是热力图是
  20 行 × 24 列以上的矩阵，大模型抄不准 —— 它会把图案「重写」一遍，
  看起来像模像样，但和页面数据对不上
- 模型只拿到关键数字（渠道数、请求合计、缓存率最高/最低），负责写评论；
  后端把评论与真实热力图拼成一张图
- 渲染器仍保留 emoji → 色块的能力（🟩🟨🟧🟥⬜ 等画成真正的圆角色块）：
  内置中文字体不含 emoji 字形，当文字画会变成空白或豆腐块，
  而模型偶尔仍会自己塞 emoji

其它内容则走通用 Markdown 解析：表格画成表格、标题画成分节、普通文字画成段落。

中文字体**随 JAR 打包**，不依赖运行环境装字体：

| 项 | 值 |
|---|---|
| 文件 | `backend/src/main/resources/fonts/wqy-microhei.ttc` |
| 字体 | 文泉驿微米黑（WenQuanYi Micro Hei） |
| 许可证 | Apache-2.0（或 GPL-3+ with Font exception，本项目按 Apache-2.0 使用） |
| 来源与校验 | 同目录 `NOTICE.txt` / `SHA256SUMS.txt` |

> 为什么内置而不是装系统字体：JRE 自带字体不含中文，靠系统字体很容易出现
> 「本地能跑、容器里变豆腐块」。内置之后连构建期联网都不需要，
> 本地开发、CI、容器的渲染结果也完全一致。

`MONITOR_BOT_IMAGE_FONT` 可以改用系统字体（一般不用改）。万一内置字体缺失，
渲染器会自动退回系统字体探测；都不可用时退回截断文本。

**启动时就会自检并打一行结论**，部署后直接查日志即可确认：

```bash
grep "图片渲染" /app/monitor/logs/monitor.log | tail -1
```

| 日志 | 含义 |
|---|---|
| `QQ 机器人图片渲染就绪：内置字体 WenQuanYi Micro Hei` | 正常 |
| `QQ 机器人图片渲染就绪：系统字体 ...` | 内置字体缺失，退回了系统字体 |
| `QQ 机器人图片渲染不可用：没有可用中文字体，长回复将退回截断文本` | 有问题，需要排查打包 |
| `QQ 机器人图片渲染已关闭（MONITOR_BOT_IMAGE_ENABLED=false），长回复按文本截断` | 手动关掉了 |

真正发图时还会打一条 INFO，可以用来确认功能确实在触发：

```
回复过长（1234 字），已转为图片发送: user=10001, bytes=39961
```

不需要这个功能时把 `MONITOR_BOT_IMAGE_ENABLED` 设为 `false` 即可。

## 4. 天气查询（所有人都能用）

和平台无关的功能，因此**三种人设都会挂载** —— 陌生人也能正常问天气，
它不涉及任何平台数据，不违反「陌生人看不到平台信息」的约束。

| 用法 | 说明 |
|---|---|
| `/天气 北京` | 实时天气 + 默认 3 天预报 |
| `/天气 北京 7` | 指定预报天数（0-7，0 表示只查当前天气） |
| 直接说人话 | 「上海今天天气怎么样」「Tokyo 明天会下雨吗」 |

数据来自 [uapis.cn](https://uapis.cn/docs/api-reference/get-misc-weather) 的免费天气接口，
**无需注册、无需 API Key**。支持中文（北京）与英文（Tokyo）城市名。

返回内容包括实时天气、体感温度、湿度、风力、空气质量（AQI 与首要污染物）、
紫外线、能见度、气压，以及逐日预报。有官方气象预警时会在底部标出。

**输出是给人直接读的纯文本，不含 Markdown 表格**：

```
北京 · 实时天气
天气：晴
温度：26°C（体感 25°C）
湿度：34%
风力：东风 1级
空气质量：优（AQI 49，首要污染物 O3）
紫外线：4
能见度：11.3 km
气压：1013 hPa
更新时间：10-10 16:34
未来 3 天
10-10 星期六  多云转晴  26/14°C  降水 0%
10-11 星期日  阴转小雨  25/15°C  降水 30%
10-12 星期一  多云转晴  23/14°C  降水 10%
```

几点刻意的取舍：

- 预报**逐天一行**，不用表格 —— 竖线和 `|---|` 在 QQ 里读起来很别扭
- 白天夜间不同时写成「多云转晴」，相同时只写一个
- 温度写 `26/14°C` 而不是 `26°C / 14°C`，更紧凑
- 更新时间去掉年份与秒；接口返回「11 分钟前发布」这类相对时间时原样保留

> **免费额度按次计（2 积分/次）**，所以默认对同一城市缓存 10 分钟，
> 群里反复问同一个城市不会每次都打接口。缓存时长可用 `MONITOR_WEATHER_CACHE_TTL` 调整。

城市名写错时接口返回 404，机器人会提示「换个写法试试」，而不是抛错。
## 4. 身份识别与管理员（谁能查平台数据）

平台功能要**双重命中**才触发：先**按邮箱**认出是谁，再要求消息落在**「指定群」**上下文里 ——
两者都命中才给平台功能。这直接关系到平台数据会不会泄露。

```
QQ 消息 ──► QQ 号 ──┬─► 显式绑定（/绑定 <邮箱>）      ──► 邮箱
                    └─► 自动匹配（<QQ号>@qq.com）    ──► 邮箱
                                     │
                                     ▼
                 邮箱是否在「平台用户」名单里？（Redis 缓存）
                          │                        │
                         是                        否
                          ▼                        ▼
              平台用户（管理员 / 普通）          普通聊天机器人
                          │                  └─ 无平台工具、提示词禁止提及平台，
                          ▼                       平台级命令一律回「未知命令」
          消息是否落在「指定群」上下文里？
          （群聊取本群；群临时会话取发起群）
                  │                    │
                 是                    否
                  ▼                    ▼
          监控助手（平台功能）    普通聊天机器人
          ├─ 管理员：全部只读工具   （好友私聊一律走这条：
          └─ 普通用户：无平台工具，   不给平台功能，只给绑定 / 天气 / 聊天）
             平台数据只回「仅管理员可查」
          ※ 管理员例外：好友私聊 / 群临时会话直接放行
```

### 数据来源

平台用户邮箱来自自建 Sub2API 的只读库 `public.users`（只取 `email` / `role` / `status`，
过滤掉软删除），由定时任务 `sub2api-user-sync` 默认每 10 分钟同步到 Redis。

只读账号需要额外授权：

```sql
GRANT SELECT ON public.users TO monitor_ro;
-- 机器人管理端的 /订单、/用户余额 直连只读库读订单，需要这一条
GRANT SELECT ON public.payment_orders TO monitor_ro;

> `/用户消耗` 的口径：`SUM(usage_logs.actual_cost) WHERE billing_type = 0`。
> `actual_cost` 是「实际扣除费用」，`billing_type = 0` 表示扣的是**钱包余额**（1 是订阅套餐），
> 所以这个报表只含余额消耗、不含套餐消耗。`usage_logs` 的 SELECT 权限号池增量采集已经在用，
> 关联用户邮箱还要 `public.users`（上面第一条）。按 Asia/Shanghai 的自然日统计。
```

> `/订单` 为什么走直连库：Sub2API 的 `GET /api/v1/admin/payment/orders` 只支持
> `user_id` / `status` / `order_type` / `payment_type` / `keyword` 加翻页，**没有日期范围**；
> 而 `payment_orders` 上有 `(user_id)` 与 `(created_at)` 索引，直连库才做得到按日期范围过滤。
> 读取时只取建表就存在的列，后续迁移新增的 `out_trade_no` / `provider_key` /
> `provider_snapshot` / `bonus_amount` 一概不碰，避免部署版本没跑到那些迁移时报列不存在。

> `/渠道状态` 走 Sub2API 被动渠道监控 v2 的聚合表 `channel_monitor_v2_metrics_1m`
> （主键 `(bucket_start, platform, group_id, model)`，**按分组聚合是原生维度**）。
> 口径对齐 Sub2API：请求数 = 成功 + 失败；缓存率 = `cache_read / (input + cache_creation + cache_read)`，
> **分母不含 output**。可见范围对齐它的 `scopeFilter`：订阅型分组要有有效订阅，
> 标准分组默认公开，专属分组或开了 `restrict_public_groups` 的用户要落在 `user_allowed_groups` 里。
> 报表不展示 RPM / TPM，因此不涉及上游的 `channel_monitor_hide_throughput` 脱敏。
> 只读账号需要额外授权：`channel_monitor_v2_metrics_1m`、`groups`、`user_subscriptions`、`user_allowed_groups`。

> 未配置只读库或未授权时，任务每轮直接跳过，机器人退化为「所有人都是普通聊天」——
> 不会报错，也不会误判成平台用户。

### 管理员：两个来源取并集

Sub2API 只允许**一个**管理员账号，实际运维往往需要多人分担，因此管理员有两个来源：

| 来源 | 说明 |
|---|---|
| Sub2API 自带 | `public.users.role = 'admin'` 的用户 |
| 自定义名单 | 在**「系统设置」页 → 身份识别与管理员**卡片里登记的邮箱，保存在监控项目自己的库里 |

**任一命中即为管理员**。自定义管理员即使不是 Sub2API 用户，也能以监控助手（管理员）身份使用机器人。
页面同时展示 Sub2API 侧的缓存人数、管理员数与最近同步时间，并提供「立即同步用户」按钮。

### 谁在什么通道能用平台功能

| 通道 | 身份 | 平台功能 |
|---|---|---|
| 群聊（**指定群**） | 管理员 | ✅ 全部只读查询工具 |
| 群聊（**指定群**） | 普通用户 | ✅ 只能查**自己**（余额 / 用量 / 密钥）；平台级数据仍回「仅管理员可查」 |
| 群聊（启用群但**非指定群**） | 任何人 | ❌ 普通聊天，平台级命令回「未知命令」 |
| 群临时会话（**发起群是指定群**） | 管理员 | ✅ 全部只读查询工具 |
| 群临时会话（**发起群是指定群**） | 普通用户 | ✅ 同「指定群普通用户」，只能查自己 |
| 群临时会话（发起群非指定群 / 取不到群号） | 任何人 | ❌ 普通聊天 |
| **好友私聊** | 管理员 | ✅ 全部只读查询工具 |
| **好友私聊** | 普通用户 / 陌生人 | ❌ 只给正常功能（绑定、天气、聊天） |

> **群临时会话的唯一限制是来源群**：只要发起它的那个群在「允许的群号」里就放行，
> **不看**发送者是否在「允许的私聊 QQ」里 —— 临时会话本质是「群成员跟机器人说话」，
> 权限继承自群，和群里 @机器人 保持一致。取不到群号时按不在白名单处理（fail-closed）。
>
> 「允许的私聊 QQ」只管**好友私聊**，用来拦住陌生人加好友后直接私聊。
> 三种通道的判定：群聊 / 群临时会话 → 只看群；好友私聊 → 只看 QQ。
>
> 被拦下时会在日志里打一条 info（`忽略非白名单会话: channel=…, 来源群=…, user=…`），
> 便于排查「机器人为什么不回我」——这条以前是 debug，默认日志级别下完全无痕。

> 对**没有平台功能**的会话（陌生人、非指定群、好友私聊里的普通用户），机器人绝不会出现任何
> 平台相关信息：没有工具、系统提示词明令禁止提及平台，连 `/help` 都只列出绑定与解绑。
> 这是刻意的硬约束。

**边界用「白名单式禁词」表达**：提示词把禁区压缩成一份词表（平台 / 上游 / 账号 / 余额 /
额度 / 号池 / 密钥 / 监控 / 采集），并明确「除这些之外都正常回答」。早期写法用
「硬性规则，任何情况下都不能违反：你不知道……」开头，小模型会把它泛化成「我什么都答不了」——
连问一句「2026-10-10 黄历怎么样」都会被回成「我查不了，要不要帮你看看天气」。
现在凡是不沾平台的话题（天气、日期、农历、黄历、常识、闲聊）都正常回答；
拿不准的（农历日期、黄历宜忌）补一句「可能有出入」而不是拒答 ——
工具清单不是能力边界，这是给「路人」重新划线的核心。

### 「指定群」怎么配

「系统设置」页 → QQ 机器人 卡片里的**指定群（平台功能）**是独立配置项，必须是
**「允许的群号」的子集**（保存时校验，越界会被拒绝）。

- 「允许的群号」决定机器人在哪些群**会响应**；
- 「指定群」决定在哪些群**才给平台功能**；
- 指定群**留空 = 任何群都不给平台功能**（fail-closed，与白名单「留空 = 不限制」相反）。

群**临时会话**按「发起该会话的群号」判定：只有从指定群发起的临时会话才算命中。
若 OneBot 实现没带 `group_id`，按「不在指定群」处理（fail-closed），
日志里会打印 `收到群临时会话: user=..., 发起群=..., 触发平台功能=...` 便于排查。

### 一个刻意的取舍

`/绑定` 的回复与邮箱是否命中平台用户**完全无关**（统一回「已记录你的邮箱。」），
否则任何人都能靠反复绑定邮箱、观察回复差异来枚举出哪些邮箱是平台用户。

代价是：绑定了一个并非平台用户的邮箱时，用户不会收到任何提示，只会继续以普通聊天身份对话。

## 6. 生图（所有人都能用）

`/画图 <提示词>`，或直接说「画一只橘猫在看雪」。

| 项 | 说明 |
|---|---|
| 接口 | OpenAI 兼容的 `POST {base-url}/v1/images/generations`，与聊天模型可共用同一个中转 |
| 模型 | `MONITOR_IMAGE_GEN_MODEL`，默认 `gpt-image-2.5`（同系列还有 `-flare` / `-sunburst`） |
| 返回 | 上游给的是 `data[0].b64_json`，后端直接解码成字节再发出去，不走外链 |
| 限频 | **全局滑动窗口：不分人、不分群，一分钟合计最多 3 张**（`MONITOR_IMAGE_GEN_MAX_PER_MINUTE`） |
| 耗时 | 实测 1024x1024 约 24 秒 —— 所以机器人消息线程池从 2 调到 4，避免生图把其它消息堵住 |

> 为什么限频是**全局**的：生图一次 20 秒以上且要花钱/耗额度，必须有个总闸。
> 被限时会直接告诉用户「一分钟最多 3 张，约 N 秒后再试」。

### 会话记忆怎么隔离

记忆作用域是 **人设 + 通道 + 说话的人**：

| 通道 | 作用域 | 说明 |
|---|---|---|
| 群聊 | `qq-group-<群号>-<QQ>` | 同一个群里**每人一段**，不共用 |
| 好友私聊 | `qq-user-<QQ>` | 每人一段 |
| 群临时会话 | `qq-temp-<发起群>-<QQ>` | 与好友私聊分开，避免指定群里的内容漏进私聊 |

> 群聊早期只用了群号（`qq-group-<群号>`），导致**整个群共用一段记忆**。Spring AI 的
> `MessageWindowChatMemory` 存的是一串没有署名的 user / assistant 消息，模型分不清哪句是谁说的，
> 于是甲说过的话会出现在乙的上下文里 —— 表现就是「把别人的聊天内容加到了另外的人身上」。
>
> 代价：群里不再有跨用户的共享上下文（「他刚才说的那个」这类指代会失效）。
> 要恢复共享又不串人，得让每一轮都带上说话人标签，那是另一套记忆实现。

仍然留在环境变量里的只有「部署级接线参数」，因为它们要和 NapCat 侧保持一致：

| 环境变量 | 作用 |
|---|---|
| `MONITOR_BOT_ENABLED` | 总开关：false 时回调接口直接 404 |
| `MONITOR_BOT_WEBHOOK_TOKEN` | 与 NapCat 上报共用的密钥（用于校验 X-Signature） |
| `MONITOR_BOT_API_BASE_URL` | OneBot HTTP API 地址，默认 `http://napcat:3000` |
| `MONITOR_BOT_API_TOKEN` | OneBot HTTP API 的 access token，一般留空 |

## 7. 开启自然语言问答（可选）

默认 `SPRING_AI_MODEL_CHAT=none`，不配 Key 也能正常启动。要开启对话：

```dotenv

SPRING_AI_OPENAI_API_KEY=sk-...
```

## 8. 消息存档（事后查证）

机器人会替人回答问题，也可能被拿来做纠纷举证，因此收发的消息都会存档：
**谁在什么时候说了什么、机器人回了什么、当时是什么身份**。

### 怎么查

「消息存档」页面（仅管理员可见）：支持按**内容关键字 / QQ 号 / 群号 / 时间范围**查询，
时间倒序展示。每条记录包含：

| 字段 | 说明 |
|---|---|
| 方向 | 收到（用户发的）/ 回复（机器人发的） |
| 来源 | 私聊还是群聊、QQ 号与群号 |
| 身份 | **存档时的快照**：管理员 / 平台用户 / 陌生人 |
| 人设 | 机器人用什么身份回答的（监控助手 or 普通聊天） |
| 内容 | 消息正文；图片消息存的是图片上的文字 |

身份和人设都存**快照**，这样日后身份变了也能解释「当时为什么那样回答」。

### 四个设计要点

1. **全异步写入**：调用方只生成一个关联 ID 就把写入丢进队列，**不等待数据库** ——
   存档绝不能拖慢机器人回复。有一条单测专门验证这点（写库卡住 5 秒，调用方仍在 200ms 内返回）。
2. **关联 ID 由应用生成**（不是数据库自增），所以「用户消息」和「机器人回复」两条记录
   可以完全独立、乱序写入，不依赖写入先后。
3. **写入是旁路**：队列满、数据库出错都只记日志，绝不抛异常影响回复。
   队列满时丢**最旧**的一条（最近的消息对查证更有价值）。
4. **图片消息存文字**：图片本身不入库，存的是图片上的文字内容，这样关键字也能搜到。

### 保留策略

默认保留 **90 天**，每天凌晨 4 点由定时任务「机器人消息存档清理」清理旧记录。
把 `MONITOR_BOT_ARCHIVE_RETENTION_DAYS` 设为 `0` 或负数即永久保留。

### 隐私提醒

存档会记录用户发的原话（可能包含邮箱等个人信息）。查询接口仅 ADMIN 可访问。
如果面向他人提供服务，建议在机器人帮助里说明消息会被记录。

## 9. 安全

- **用户端只能查自己**：`/我的余额` `/我的用量` `/我的密钥` 的查询主体是发送者邮箱解析出的用户 ID，
  没有「传别人的 ID」这个入口；管理员密钥只存在服务端，不随回复下发。
- 回调接口 `/api/v1/bot/onebot` 没有登录会话，**完全依赖共享密钥**：
  未配置 `MONITOR_BOT_WEBHOOK_TOKEN` 时直接返回 404，密钥不匹配返回 403。
- 建议同时配置 `MONITOR_BOT_ALLOWED_GROUPS` / `MONITOR_BOT_ALLOWED_USERS`，避免被拉进陌生群乱问。
- 机器人只读：暴露给模型的工具全部是查询接口，没有写操作。

## 10. 排查

| 现象 | 排查方向 |
|---|---|
| 机器人没反应 | 看本服务日志有没有收到 `POST /api/v1/bot/onebot`；没有就是 OneBot 上报地址/网络不通 |
| 日志 403 | 两边 `Authorization` 与 `MONITOR_BOT_WEBHOOK_TOKEN` 不一致 |
| 日志 404 | `MONITOR_BOT_ENABLED` 不是 true，或密钥没配 |
| 群里不回、私聊回 | `MONITOR_BOT_REQUIRE_MENTION=true` 时需要先 @机器人 |
| 回复「处理这条消息时出错了」 | 大概率是 OneBot 的 HTTP API 地址或 token 配错，看同一时间的 WARN 日志 |
