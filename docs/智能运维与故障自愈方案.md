# Monitor × Sub2API 智能运维与故障自愈方案

> 版本：v0.1  
> 目标：先落地「方向 9：故障指挥与 QQ 运维助手」，并以此为基础逐步建设完整的智能故障自愈体系。

---

## 1. 目标与边界

### 1.1 目标

让 Monitor 成为 Sub2API 的**外环智能控制面**：

```text
Monitor 采集两平台数据
→ 识别故障
→ 归因分析
→ 生成自愈预案
→ 风险评估
→ 自动执行或管理员确认
→ 回读验证
→ 记录、回滚、复盘
```

最终减少以下人工操作：

- 反复查看 Sub2API 后台
- 手动清理账号限流/错误
- 手动暂停或恢复账号
- 手动切换分组 fallback
- 手动调整用户并发/RPM
- 手动追查错误与变更关系
- 手动处理支付履约异常

### 1.2 边界

本方案不把 Monitor 做成第二个 Sub2API，也不直接写 Sub2API 数据库。

原则：

1. **读数据可以使用只读库和 Admin API。**
2. **写操作统一调用 Sub2API Admin API。**
3. **所有自动动作必须可审计、可验证、可回滚。**
4. **大模型不直接执行写操作。**
5. **高风险动作必须人工审批。**

### 1.3 不做什么

第一版不做：

- 自动删除账号或用户
- 自动修改用户密码
- 自动修改支付渠道
- 自动退款
- 自动修改安全配置
- 直接 SQL 写入 Sub2API 业务表
- 让大模型自由拼接 SQL 或任意 HTTP 请求

### 2.3 现有缺口

1. API Key 级管理能力不足  
   当前 Admin API 对 API Key 主要支持改分组和重置限速用量，不能直接修改状态、额度、IP 白名单。

2. 敏感操作受 step-up 2FA 限制  
   Sub2API 开启 step-up 后，部分接口会拒绝 Admin API Key，只接受完成二次验证的 JWT 会话。

3. 缺少统一的故障事件模型  
   目前错误、账号、分组、变更、告警分散在不同数据源，需要先关联成事故。

4. 缺少持久化的动作审批  
   现有充值确认流程可以作为参考，但事故动作必须持久化，不能只存在内存。

## 4. 方向 9：故障指挥与 QQ 运维助手

### 4.1 定位

方向 9 是整个智能运维体系的**统一入口和指挥层**，负责：

- 故障发现后主动通知
- 查询故障、账号、分组、用户、变更
- 生成自愈计划
- 展示影响范围和风险
- 管理员确认后执行
- 执行后回读验证
- 失败时回滚
- 形成事故时间线和复盘

它不是简单的 QQ 命令机器人，而是：

> **故障事件中心 + 动作计划中心 + 审批中心 + 审计中心**

### 4.2 使用通道

| 通道 | 能力 |
|---|---|
| 管理员好友私聊 | 查看原始明细、生成计划、确认执行、回滚 |
| 指定群 | 只读查看脱敏后的故障摘要 |
| 群临时会话 | 只读查看脱敏后的故障摘要 |
| 普通用户私聊 | 不允许访问平台运维信息 |
| 陌生人 | 不允许访问平台运维信息 |

所有写操作只允许管理员好友私聊。

### 4.3 核心能力

#### A. 故障查询

示例：

```text
/事故
/事故 #1024
/事故 近1小时
/事故 分组
/事故 账号
/事故 用户
/事故 变更
```

自然语言示例：

```text
现在有什么故障？
最近一小时哪个平台错误最多？
分组 A 为什么一直 503？
哪个账号的限流一直没有恢复？
刚才改了什么导致错误突增？
```

#### B. 故障诊断

返回内容：

- 故障等级
- 首次发生时间
- 最近发生时间
- 影响平台
- 影响分组
- 影响模型
- 影响账号
- 影响用户/Key
- 错误分布
- 关联变更
- 疑似根因
- 建议动作

#### C. 自愈计划

示例：

```text
/自愈 账号 123
/自愈 分组 A
/自愈 事故 #1024
```

自然语言示例：

```text
帮我恢复所有已经过了限流时间的账号。
把错误率最高的三个账号暂停 30 分钟。
把分组 A 切到 fallback。
检查这次故障能不能自动回滚。
```

系统只生成计划，不立即执行：

```text
自愈计划 #P1024

目标：账号 123、账号 456
原因：连续 502 空响应，最近一次测试失败
动作：
1. 暂停账号 123 调度 10 分钟
2. 暂停账号 456 调度 10 分钟
3. 10 分钟后自动测试
4. 测试通过自动恢复

影响：预计减少约 18% 可用账号
回滚：恢复原调度状态
风险：中
确认码：A1B2C3D4
回复：确认执行 A1B2C3D4
```

#### D. 执行与验证

执行流程：

```text
确认执行
→ 检查确认码
→ 检查操作人权限
→ 检查冷却时间
→ 检查影响范围
→ 保存执行前快照
→ 调用 Sub2API
→ 回读状态
→ 指标验证
→ 成功/失败/回滚
→ 推送结果
```

#### E. 回滚

```text
/回滚 #P1024
/确认回滚 A1B2C3D4
```

回滚只适用于低风险配置类动作：

- 可调度状态
- 优先级
- 并发
- 分组 fallback
- 模型映射
- 分组倍率（高风险，需审批）

#### F. 事故复盘

```text
/事故报告 #1024
```

生成：

- 事故摘要
- 时间线
- 根因
- 影响范围
- 已执行动作
- 恢复过程
- 建议改进项

### 4.4 交互模式

建议支持三种模式：

| 模式 | 行为 |
|---|---|
| OBSERVE | 只查询、只告警，不生成可执行计划 |
| SUGGEST | 生成计划，但必须管理员确认 |
| AUTO_SAFE | 低风险动作自动执行，并通知结果 |
| APPROVAL | 中高风险动作必须审批 |
| BLOCKED | 当前故障类型禁止自动处理 |

每个策略独立配置模式。

### 4.5 大模型与确定性命令的关系

- 确定性命令不依赖大模型，保证大模型故障时仍可用。
- 大模型用于自然语言理解、故障解释、计划生成。
- 写操作必须通过专用工具，工具内部再次校验：
  - 当前用户是管理员
  - 当前通道是好友私聊
  - 当前消息包含确认码
  - 确认码未过期
  - 动作与计划一致
  - 幂等键未使用

## 5. 完整方向清单

## 方向 1：统一故障归因与事件图谱

### 目标

把分散的错误、账号状态、用量、变更、告警聚合成一个故障事件。

### 输入

- `ops_error_logs`
- `usage_logs`
- `channel_monitor_v2_metrics_1m`
- `accounts`
- `groups`
- `api_keys`
- `users`
- `proxies`
- Monitor 变更事件
- Monitor 告警记录

### 故障分类

| 分类 | 典型信号 |
|---|---|
| 账号认证故障 | 401/403、account_auth |
| 账号限流 | 429、rate_limit_reset_at |
| 账号过载 | 529、overload_until |
| 账号空响应 | 502、empty response |
| Provider 故障 | 多账号同平台同模型异常 |
| 网络/代理故障 | network、timeout、proxy expired |
| 容量故障 | queue full、concurrency limit、no accounts |
| 配置故障 | model_not_found、model mapping mismatch |
| 用户/Key 故障 | invalid key、IP blocked、abuse |
| 计费/订阅故障 | billing_error、subscription_error |
| 客户端故障 | invalid_request_error、cyber_policy |

### 关键原则

**先归因，再动作。**

不能因为一个请求失败就直接暂停账号。

Sub2API 源码中已经有账号级、Provider 级、Request 级故障语义，应优先复用：

- `GatewayFailureStage`
- `GatewayFailureScope`
- `RequestScopedTransient`
- `NextAccountAction`

参考：

- `E:/code/sub2api/backend/internal/service/gateway_service.go`
- `E:/code/sub2api/backend/internal/handler/failover_loop.go`
- `E:/code/sub2api/backend/internal/service/ops_user_error.go`

## 方向 2：账号健康自愈

### 目标

让账号从异常状态自动恢复到可调度状态，减少人工清理限流和错误。

### 状态机

```text
HEALTHY
→ SUSPECTED
→ TESTING
→ TEMP_PAUSED
→ RECOVERING
→ HEALTHY
```

### 规则

| 条件 | 动作 |
|---|---|
| 限流恢复时间已过且仍不可调度 | clear-rate-limit |
| 错误持续但最近测试成功 | clear-error / recover-state |
| OAuth 401/403 | refresh，失败后暂停并通知 |
| 多次 529 | 降低优先级，等待冷却 |
| 502 空响应 | 临时暂停并测试 |
| 账号配额耗尽 | 暂停，等待额度重置 |
| 连续测试通过 | 恢复可调度 |

### 安全限制

- 同一账号 30 分钟内最多自愈 2 次
- 同一故障指纹只处理一次
- 手动暂停的账号不自动恢复
- Provider 级故障不处罚单账号
- 账号删除永远不自动执行

---

## 方向 3：上游平台故障隔离与自动降级

### 目标

区分单账号故障和 Provider 故障，避免批量误伤。

### 判断

```text
单账号异常 → 账号自愈
多账号同平台异常 → Provider 故障
同模型跨平台异常 → 模型/请求故障
全部分组异常 → 系统级故障
```

### 动作

- 切换分组 fallback
- 降低分组流量
- 暂停指定模型
- 调整模型映射
- 限制用户 RPM
- 提高备用账号优先级
- 恢复后逐步放量

### 数据

- 渠道监控 v2
- 错误日志按平台/分组/模型聚合
- 账号可用数
- Monitor 历史基线

## 方向 4：容量与并发自愈

### 信号

- `gateway_queue_full`
- `gateway_concurrency_limit`
- 分组可用账号低于安全线
- 账号并发利用率长期超过 90%
- 429 大量出现但账号未真正限流
- 峰值请求量超过历史基线

### 动作

- 提高健康账号并发
- 降低低优先级账号权重
- 降低用户 RPM
- 切换 fallback
- 生成扩容建议

第一阶段不建议自动创建账号或导入凭证。

## 方向 5：代理与网络故障自愈

### 信号

- network 阶段错误

### 动作

- 切换 fallback proxy
- 切换 direct
- 暂停受影响账号
- 恢复原代理
- 标记代理异常
- 通知管理员更新代理

## 方向 6：变更引发的故障自动回滚

### 流程

```text
保存变更前快照
→ 记录变更
→ 观察 5～30 分钟
→ 错误率/延迟/成本异常
→ 关联变更
→ 生成回滚计划
→ 低风险自动回滚
→ 高风险人工确认
```

### 适合自动回滚

- 账号优先级
- 账号并发
- 账号可调度状态
- 分组 fallback
- 模型映射
- 模型白名单
- 分组 RPM

### 不适合自动回滚

- 用户密码
- 用户角色
- 支付配置
- 上游凭证
- 删除操作

## 方向 7：用户与 API Key 故障隔离

### 信号

- 单用户请求量突增
- 大量无效请求
- 大量 401/403
- 入口拒绝
- 同一 Key 多 IP
- 风控违规
- 余额/订阅不足
- Key 配置错误

### 动作

- 降低用户并发
- 降低用户 RPM
- 调整平台额度
- 暂停用户
- 重置 Key 限速用量
- 切换 Key 分组

当前 Admin API 不能直接修改 API Key 的状态、额度、IP 白名单。

建议后续增加：

```text
PUT /api/v1/admin/api-keys/:id
```

支持：

- status
- quota
- ip_whitelist
- ip_blacklist
- expires_at
- rate_limit_5h/1d/7d

## 方向 8：支付与订阅可用性自愈

## 7. 策略引擎设计

每个策略由四部分组成：

### 7.1 触发条件

```text
错误率 > 20% 持续 5 分钟
账号连续 3 次 502
分组可用账号数 < 2
代理 3 天内过期
```

### 7.2 前置守卫

```text
不是 Provider 级故障
不是手动暂停
不在维护窗口
冷却时间已过
影响范围未超限
```

### 7.3 动作计划

```text
暂停账号
清理限流
切换 fallback
降低用户 RPM
```

### 7.4 验证与回滚

```text
执行后 2 分钟回读
错误率下降
账号恢复可调度
如果失败则回滚
```

## 11. 分阶段实施计划

### 阶段 0：数据与事故模型

目标：先把故障看清楚。

- 新增事故表、信号表、时间线表
- 统一错误分类
- 建立故障指纹
- 关联账号、分组、模型、用户、变更
- 只读展示，不执行动作

验收：

- 能查询当前事故
- 能看到错误分布和影响范围
- 能关联最近变更
- QQ 管理员私聊可收到事故摘要

### 阶段 1：方向 9 最小闭环

目标：让 QQ 成为故障指挥入口。

- 事故查询
- 事故详情
- 事故时间线
- 自愈计划生成
- 确认码
- 执行记录
- 管理员私聊权限校验
- 群聊脱敏摘要

验收：

- 管理员可在 QQ 私聊查看事故
- 可生成计划
- 必须确认码才能执行
- 所有动作有审计
- 大模型不可用时确定性命令仍可用

### 阶段 2：安全自动自愈

目标：减少低风险人工操作。

- 清理过期限流
- 清理过期错误
- 恢复健康账号
- 刷新 OAuth
- 调整并发/RPM

验收：

- 自动动作有冷却
- 自动动作有回读验证

- 失败可回滚
- 不误伤 Provider 级故障

- Provider 故障识别
- 分组 fallback
- 容量降级
- 代理切换
- 恢复后逐步放量

### 阶段 4：变更回滚与高级自愈

- 变更前快照
- 变更后异常关联
- 低风险自动回滚

## 12. 验收标准

### 功能

- 故障发现后 1～2 分钟内生成事故
- 管理员 QQ 私聊可收到事故摘要
- 可按平台、分组、账号、用户、模型查询
- 可查看事故时间线
- 可生成自愈计划
- 可审批、执行、回滚
- 可查看执行结果和验证结果

### 安全

- 只有管理员好友私聊能执行写操作
- 群聊和其他用户只能看脱敏信息
- 所有写操作有确认码
- 所有写操作有幂等键
- 所有写操作有审计记录
- 高风险动作不能自动执行
- 单次动作影响范围有上限

### 稳定性

- 大模型不可用时命令仍可用
- Sub2API 不可用时不会重复执行动作
- 执行超时不会重复扣款/重复恢复
- 事故通知有去重和静默
- 动作失败自动停止并告警

## 14. 推荐的第一版

第一版建议只做：

```text
事故中心（只读）
+ QQ 管理员查询
+ 自愈计划生成
+ 确认码审批
+ 动作执行记录
```

暂不自动写 Sub2API。

第二版再开启：

```text
清理过期限流
清理过期错误
恢复健康账号
刷新 OAuth
```

第三版再开启：

```text
分组 fallback
容量降级
代理切换
变更回滚
```

这样可以在不牺牲线上稳定性的前提下，逐步把 Monitor 建设成 Sub2API 的智能运维控制面。
