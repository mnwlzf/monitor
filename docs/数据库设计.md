# 数据库设计

## 目标

数据库需要同时支撑三类能力：

1. 保存账号余额、额度、请求数等指标，作为折线图的数据源。
2. 保存上游渠道/分组的当前状态和历史快照。
3. 为后续采集结果对比预留变更事件模型，用于检测渠道增加、减少、倍率变化等。

## 核心原则

- **时序数据追加写入**：账号指标和分组指标只追加快照，不覆盖历史数据。
- **当前状态单独维护**：`upstream_groups` 保存最新状态，便于快速对比和列表展示。
- **原始响应保留**：`raw_data` 使用 `JSONB`，上游新增字段时不需要立即改表。
- **通用指标显式建模**：余额、额度、倍率等高频查询字段使用独立数值列，避免每次查询解析 JSON。
- **变化事件统一记录**：`upstream_change_events` 使用多态实体设计，后续可扩展到 API Key、模型、渠道状态等。
- **采集批次可追踪**：所有快照和变更事件都可关联 `collection_runs`。

## 表关系

```text
platforms
  └─ accounts
       ├─ account_credentials
       ├─ collection_runs
       ├─ account_metric_snapshots
       ├─ upstream_groups
       │    └─ upstream_group_snapshots
       └─ upstream_change_events
```

## 表职责

### collection_runs

记录一次账号采集的执行情况，包括开始时间、结束时间、耗时和错误信息。所有采集产生的数据都通过 `collection_run_id` 关联到批次。

### account_metric_snapshots

账号级时序快照，适合折线图查询。

主要字段：

- `balance`：可用余额，例如 Sub2API。
- `frozen_balance`：冻结余额。
- `quota`：剩余额度，例如 New API。
- `used_quota`：历史使用额度。
- `request_count`：累计请求数。
- `quota_unit`：额度单位或换算说明。
- `raw_data`：完整原始响应。
- `content_hash`：内容哈希，用于去重和判断是否真正变化。

### upstream_groups

渠道/分组当前状态表。当前接口中 Sub2API 称为 group，New API 也称为 group，本表统一按“渠道/分组”处理。

唯一键：

```text
(account_id, platform_type, external_group_id)
```

其中：

- Sub2API：`external_group_id` 使用上游 `id`。
- New API：`external_group_id` 使用分组名称，因为该接口返回的是动态 Map。

### upstream_group_snapshots

渠道/分组历史快照。每次采集后追加一条，记录当时的倍率、基础倍率和状态。

### upstream_change_events

变更事件表，预留给后续对比逻辑。典型事件：

- `GROUP_ADDED`
- `GROUP_REMOVED`
- `RATE_CHANGED`
- `STATUS_CHANGED`
- `ACCOUNT_BALANCE_CHANGED`
- `API_KEY_QUOTA_CHANGED`

事件同时保存 `old_value` 和 `new_value`，方便前端展示变化前后内容。

## 账号与平台设计

平台和账号是采集系统的基础数据。没有平台配置和可用账号，采集任务无法确定上游地址、认证方式和采集参数。

### platforms

`platforms` 表示一个具体上游平台实例，而不是平台类型。例如：

- 平台类型：`newapi`
- 平台实例：`yunmian`、`newapi-a`

主要字段：

- `platform_name`：平台实例名称，用于界面展示。
- `url`：平台基础地址，例如 `https://yunmian.tech`。
- `platform_type`：适配器类型，例如 `newapi`、`sub2api`。
- `settings`：平台级采集配置，JSONB，例如时区、请求参数。
- `status`：平台是否启用。
- `last_collected_at`：该平台最近采集完成时间。
- `deleted_at`：软删除时间。

### accounts

`accounts` 表示某个平台下用于登录和采集的账号。

主要字段：

- `platform_id`：关联 `platforms.id`，确定账号属于哪个平台实例。
- `email`、`username`：登录标识和展示信息。
- `display_name`：账号显示名称。
- `external_user_id`：上游返回的用户 ID，首次登录成功后回填。
- `auth_type`：认证类型，例如 `PASSWORD`、`TOKEN`、`COOKIE`、`OAUTH`。
- `credential_status`：凭证状态，例如 `UNKNOWN`、`VALID`、`INVALID`、`LOCKED`。
- `settings`：账号级采集配置，JSONB，例如 Turnstile 参数、代理配置。
- `status`：账号是否启用采集。
- `next_collect_at`：下次计划采集时间。
- `last_collected_at`、`last_collect_status`、`last_collect_error`：最近一次采集状态。
- `consecutive_failures`：连续失败次数，用于退避和告警。
- `deleted_at`：软删除时间。

账号唯一性按平台实例隔离：

```text
(platform_id, email)
(platform_id, username)
```

这样可以支持同一邮箱注册到不同平台实例。

### account_credentials

敏感凭证不直接保存在 `accounts.password`，而是拆分到 `account_credentials`：

- `credential_type`：`PASSWORD`、`TOKEN`、`COOKIE`、`OAUTH` 等。
- `encryption_algorithm`：凭证加密算法，默认 `AES_GCM`。
- `encrypted_payload`：AES-GCM 等算法加密后的凭证内容。
- `initialization_vector`：加密初始化向量。
- `key_version`：密钥版本，用于后续轮换密钥。
- `expires_at`：凭证过期时间。
- `last_verified_at`、`verification_error`：最近验证结果。
- `is_active`：是否当前启用凭证。

一个账号同一凭证类型只允许一条启用记录：

```text
(account_id, credential_type) WHERE is_active = TRUE
```

### 采集前账号解析流程

1. 按 `account_id` 查询 `accounts`。
2. 通过 `accounts.platform_id` 查询 `platforms`。
3. 校验账号和平台均未软删除、状态启用、到达 `next_collect_at`。
4. 根据 `platform.platform_type` 选择 `NewApiAdapter` 或 `Sub2ApiAdapter`。
5. 查询 `account_credentials` 中对应账号的启用凭证。
6. 解密凭证，调用上游登录接口。
7. 登录成功后回填 `external_user_id`、`credential_status`、`last_verified_at`。
8. 采集完成后更新 `last_collected_at`、`last_collect_status` 和 `next_collect_at`。
## 后续采集流程建议

1. 创建 `collection_runs`，状态设为 `RUNNING`。
2. 拉取账号信息，写入 `account_metric_snapshots`。
3. 拉取渠道/分组列表。
4. 对每个分组按唯一键查询 `upstream_groups`。
5. 不存在则新增当前态，并记录 `GROUP_ADDED`。
6. 已存在则比较倍率、基础倍率和状态，变化时更新当前态并记录 `RATE_CHANGED` 或 `STATUS_CHANGED`。
7. 本次未返回的历史分组将 `is_active` 设为 `false`，并记录 `GROUP_REMOVED`。
8. 为本次所有分组写入 `upstream_group_snapshots`。
9. 更新 `collection_runs` 为 `SUCCESS` 或 `PARTIAL`，并记录耗时。

## 典型查询

账号余额/额度折线图：

```sql
SELECT collected_at, balance, quota, used_quota
FROM account_metric_snapshots
WHERE account_id = ?
ORDER BY collected_at;
```

分组倍率折线图：

```sql
SELECT s.collected_at, s.ratio, s.base_ratio
FROM upstream_group_snapshots s
JOIN upstream_groups g ON g.id = s.group_id
WHERE g.account_id = ?
  AND g.external_group_id = ?
ORDER BY s.collected_at;
```

最近变更：

```sql
SELECT detected_at, entity_type, entity_key, change_type, old_value, new_value
FROM upstream_change_events
WHERE account_id = ?
ORDER BY detected_at DESC
LIMIT 100;
```

## 后续扩展

- API Key 级使用量可新增 `account_api_keys` 和 `account_api_key_snapshots`，沿用同样的当前态 + 时序快照模式。
- 模型价格、可用模型、渠道健康状态可以继续复用 `upstream_change_events`。
- 如果数据量增大，可按 `collected_at` 对快照表做分区或归档。
